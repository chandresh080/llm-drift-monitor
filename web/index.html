LLM Behaviour Monitor

An observability system for tracking behavioural changes in LLM applications. Versioned canary prompts are evaluated against a fixed reference window, using complementary statistical and semantic signals to identify distribution shifts and potential quality degradation.

Demonstration environment. The hosted demonstration sends its canary prompts to a live external LLM (Google Gemini 3.1 Flash-Lite) through the same monitoring pipeline the repository ships. The reference baseline was generated by Gemini itself with identical prompts, decoding settings and embeddings, so shift verdicts compare Gemini against Gemini. To protect the free tier, checks are rate limited: one run per visitor, and a shared daily cycle budget across all visitors. Stored history resets to the seeded snapshot when the hosting platform recycles the container. Live provider experiments and controlled benchmark evaluations are reported separately in the README.

Each run records 40 responses through the live model, so checks are rate limited per visitor. Statistical evaluation starts once 160 responses are stored.

Detector results

Three complementary statistical tests assess changes in response length, response availability and semantic distribution. Benjamini-Hochberg correction is applied across the test family. An individual detector flag is distinct from an operational alert, which additionally follows the configured persistence policy.

Response length ...
Kolmogorov-Smirnov test
... adjusted p-value

Compares the shape of response-length distributions between the reference and current windows.

Response availability ...
Fisher's exact test (or z)
... adjusted p-value

Tracks the share of non-empty stored answers, a conservative availability signal rather than an instruction-following or correctness measurement. This flag feeds the quality signal family, never the distribution shift verdict.

Semantic shift ...
Maximum Mean Discrepancy, permutation test
... adjusted p-value

Compares response embeddings between the windows. Because the panel probes the same prompts every cycle, the inference respects that structure: the significance test permutes complete response sets per matched prompt rather than individual responses. Details on the Evaluation tab.

Category-level analysis

Category-level tests examine whether pooled distributional changes are concentrated in particular prompt groups. Results are reported only when the distinct sample count supports inference; otherwise, the available evidence and the exclusion reason are shown.

Recent cycles and alerts

An alert is evidence, not just a warning: with the two cycle persistence rule, the same verdict must repeat on consecutive cycles before an alert fires. The persistence rule is a practical noise reduction measure, not a formal sequential error control guarantee.

Detection delay and false-alarm trade-off

The same simulated shift, four alert policies. Policies that merge evidence across cycles trade a little speed for a large reduction in noise. The shipped policy is persist2, the two cycle persistence rule. Pooled, iid simulation: the committed delay power runs predate the paired prompt level permutation, so these numbers characterise the persistence policy on pooled statistics, not the production paired alert path.

Power curves at the production window

Detection power (probability of flagging) for each test against increasing simulated shift magnitude, at the current window of 10 responses used by the original deployment. Pooled, iid simulation: these committed runs predate the paired prompt level permutation and model responses as independent draws, the structure the production path now corrects for, so read them as a characterisation of each statistic's behaviour, not as calibrated alert performance.

Prompt-level permutation analysis

The production semantic test. Because the panel probes the same prompts on both sides, responses from one prompt are not independent observations, so the significance test permutes complete response sets per matched prompt instead of individual responses. The raw p-value of this paired permutation is what enters the corrected test family and the alert path whenever matched prompt pairs exist. The response-level (pooled) permutation is retained in the stored results as an exploratory statistic. Matched prompts still limit statistical power; both the unit of permutation and the sampled versus exhaustive regime are recorded per cycle.

Recorded provider comparison: Groq versus Gemini

Recorded experiment, not a live call

A real hosted-provider comparison recorded with this pipeline on 2026-11-08: the same 10 prompt panel and generation settings sent to Groq (reference stage) and Google Gemini (current stage), using the production adapters and storage unchanged. This is cross-provider, cross-model evidence that the adapters work; it is deliberately not a drift result, because a shift between two different models could never be attributed to provider behavior alone. The hosted demo's drift verdicts compare Gemini against Gemini only.
