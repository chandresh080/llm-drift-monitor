# Design Context: llm-drift-monitor

## Product
Statistical monitoring dashboard for LLM behaviour (canary-prompt drift detection).
Hosted demo on Render free tier; vanilla HTML/CSS/JS, no framework, no build step.

## Audience
Developers and technical evaluators opening the hosted demo to judge whether the
monitoring system is credible. They read state fast, then optionally inspect
methodology and raw evidence.

## Use cases (jobs to be done)
1. Understand the current monitor verdict within five seconds of page load.
2. Trigger a check and see its quota/interval cost before committing.
3. On demand: inspect per-prompt evidence, category analysis, history, alerts,
   configuration, and evaluation benchmarks.

## Brand personality / tone
Restrained engineering tool in the style of Linear / Vercel / Stripe dashboards.
Minimal, professional, credible. NOT a marketing site, NOT an AI-generated admin
template, NOT "another giant dashboard with collapsible cards everywhere".

## Implementation defaults (established design system)
- Tokens: bg `#FAFAFA`, white surfaces, ink `#18181B`, single indigo accent
  `#4F46E5`; red/amber reserved for real alerts.
- Hairline borders (`#E4E4E7`), 6px radii, no gradients/shadows/glassmorphism.
- Type: system sans 14px base, tabular numerals for all metrics, 3 sizes.
- IA: initial viewport = header + heading/Run check + verdict + 3 metrics +
  3 detector rows + effect sizes only. Everything else collapsed `<details>`
  or the Evaluation tab.
- All values from the API; missing values render as `n/a`, never zero.
- Split signal families: distribution shift vs availability vs guardrail.

## Hard rules from the product owner
- README.md is locked; commit messages compact `[tag] message` style.
- Do not hardcode config values; the run note and configuration must reflect
  `/config` exactly (probes_per_cycle = 40 on the hosted deployment).
- Timestamps must show their actual date when old; never imply currentness.
